# Рефакторинг до «дещо універсальних» модулів

Принцип (Остерхаут, «A Philosophy of Software Design», розд. 6 і 21): **реалізація** модуля покриває лише поточні потреби, а **інтерфейс** настільки загальний, що не знає, хто і навіщо його викликає. Такий модуль глибокий: мало простих точок входу, за якими схована вся складність. Надмірна спеціалізація навпаки: кожен новий сценарій UI додає ще одну функцію в нижній шар, інтерфейс розростається, а знання про викликача протікає туди, де йому не місце.

«Модуль» тут — будь-що з інтерфейсом: файл з експортованими функціями, React-хук чи компонент, сервіс, Python-модуль `utils.py`, контролер доктайпа, набір whitelisted-методів Frappe. Класи трапляються рідко, тож думай у термінах **експортованих функцій, їхніх параметрів і типів**.

Скіл працює у дві фази з обов'язковою зупинкою між ними:
1. **Аудит і план** — нічого не змінює в коді.
2. **Виконання** — лише після явного «так» від користувача.

Ввічливо, коротко, українською. Користувач не обов'язково технічний: у підсумках пояснюй простими словами.

## Фаза 1. Аудит і план

### 1.1 Розвідка
- **Обсяг.** Аналізуй те, що назвав користувач (файл, папку, модуль, фічу). Якщо обсяг не названо — спитай. Весь репозиторій лише на пряме прохання: на великому коді аудит без фокусу дає шум.
- Перевір, що робоче дерево git чисте. Якщо ні — зупинись і попроси закомітити або відкласти зміни.
- Визнач мову, фреймворк, спосіб запуску тестів, перевірки типів (`tsc --noEmit`), лінтерів (eslint, ruff) і збірки. Для Frappe — `bench --site <site> run-tests --app <app>` і чи є доступ до стенда.
- Збери домовленості: `CLAUDE.md`, `CONTRIBUTING`, `docs/`, README, конфіги лінтерів. Записані правила важливіші за твої вподобання.
- Виключи: `node_modules`, згенерований код, збірки, історичні патчі й міграції, сторонні бібліотеки, код ядра Frappe/ERPNext.
- Залежно від мови прочитай довідку з прикладами:
  - TypeScript / React → `references/typescript.md`
  - Python / Frappe → `references/python-frappe.md`

### 1.2 Інвентаризація інтерфейсів
Для кожного модуля в обсязі склади коротку картку:
- **Інтерфейс:** експортовані функції, хуки, компоненти, whitelisted-методи, їхні параметри й типи.
- **Викликачі:** хто і скільки разів викликає кожну точку входу (пошук посилань: `tsc`/ts-morph, «Find references», ripgrep; для Frappe ще `frappe.call`, `hooks.py`, `doc_events`, рядкові шляхи `app.module.fn`).
- **Шар:** нижній (механізм, інфраструктура, утиліти, доменні примітиви) чи верхній (сторінка, форма, сценарій, обробник запиту).

Карта викликачів — головний інструмент: функція в нижньому шарі з одним викликачем і назвою, що повторює цього викликача, майже завжди спеціалізована.

### 1.3 Ознаки надмірної спеціалізації
Шукай такі запахи (приклади коду — у довідках):

1. **Контекст викликача в інтерфейсі.** Назва чи параметр нижнього модуля описує конкретну сторінку, кнопку, форму, звіт: `formatPriceForCheckout()`, `getUsersForAssigneeDropdown()`, `get_dashboard_card_data()`. Наслідок: кожна зміна UI вимагає правки нижнього шару (посилення змін).
2. **Функції-близнюки.** Кілька функцій роблять майже одне й те саме з дрібною різницею для різних клієнтів: `removeLine / removeWord / removeChar`, три копії запиту, що відрізняються одним фільтром. Наслідок: широкий і мілкий інтерфейс.
3. **Прапорці-перемикачі.** Булеві чи рядкові параметри, які вибирають поведінку під конкретного викликача: `fetchOrders(id, true, false)`, `isForAdmin`, `mode: 'modal' | 'page'`. Це близнюки, сховані в одній функції.
4. **Механізм змішаний з політикою.** Загальний механізм (retry, кеш, історія undo, черга, HTTP-клієнт, таблиця, форма, валідатор) знає про конкретні доктайпи, сутності, повідомлення UI чи бізнес-правила. Наслідок: механізм не можна використати для нової сутності без переписування.
5. **Помилкова абстракція.** Нижній модуль «ховає» те, що викликачеві насправді треба знати (як `backspace()` у класі тексту), і щоб зрозуміти поведінку, доводиться читати реалізацію.
6. **Наскрізні обгортки.** Функція лише передає виклик далі з тими самими параметрами і нічого не додає — шар без глибини.

Перевіряй і **протилежну крайність**: надмірну загальність. Параметри, generic-типи, плагінні точки й конфіги, які ніхто не використовує, теж ускладнюють код. Золота середина — простий інтерфейс під усі *поточні* сценарії, без коду під гіпотетичні майбутні.

### 1.4 Проєктування заміни
Для кожної знахідки запропонуй цільовий інтерфейс:
- **Крок 1. Розділи механізм і політику.** Механізм іде вниз і не знає, хто його кличе. Політика (що саме видалити, яке повідомлення показати, в якій послідовності діяти) іде вгору, у викликача.
- **Крок 2. Зведи до примітивів.** Групу спеціалізованих функцій заміни 1–3 примітивами на базових типах (позиції, діапазони, id, фільтри, колбеки). Високорівневі дії викликач складає з примітивів сам.
- **Крок 3. Перевір чотири питання Остерхаута:**
  1. Який найпростіший інтерфейс покриває всі поточні потреби? (менше функцій і параметрів)
  2. У скількох ситуаціях використовуватиметься ця функція? (одна ситуація — підозра на спеціалізацію)
  3. Чи легко ним користуватися для поточних задач? (типовий виклик не має ставати громіздким)
  4. Чи відокремлено загальне від специфічного? (чи знає нижній модуль щось про викликача)

Якщо нова версія не проходить питання 3 — викликачам стало важче — краще залиш як є або додай одну тонку зручну функцію *у верхньому шарі*.

### 1.5 Що не чіпати
Позначай «не змінювати» з поясненням:
- інтерфейси, продиктовані фреймворком (хуки життєвого циклу Frappe `validate`/`on_submit`, `hooks.py`, обов'язкові імена й сигнатури, React-пропси сторонніх бібліотек);
- публічний API для зовнішніх клієнтів: whitelisted-методи, які кличуть ззовні за URL `/api/method/...`, REST-ендпоінти, пакети, що публікуються;
- код, де спеціалізація виправдана: одна точка використання, проста реалізація і немає ознак, що з'являться інші;
- місця без тестів, де ризик зламати поведінку переважає користь — винеси як питання.

### 1.6 Звіти
Створи у репозиторії папку `docs/refactor-audit/` з двома файлами.

**AUDIT.md**
```
# Аудит універсальності модулів — <дата>
## Обсяг і домовленості
## Карта модулів
| Модуль | Шар | Точки входу | Викликачі |
## Знахідки
### <№>. <модуль> — <запах>
- Зараз: сигнатури як є (коротко)
- Чому це проблема: 1–2 речення, з посиланням на викликачів
- Пропоную: цільові сигнатури + як викликач складе свою дію з примітивів
- Чотири питання: коротка відповідь на кожне
## Не змінюємо (і чому)
## Відкриті питання
```

**PLAN.md** — знахідки, згруповані в порції від найменш до найбільш ризикованих:
```
## Порція 1 — низький ризик (внутрішні функції модуля, близнюки без зовнішніх викликачів)
- [ ] removeLine/removeWord/removeChar → deleteRange(start, end) · 7 викликів у 3 файлах · ззовні нічого не ламається
## Порція 2 — середній (експортовані функції, хуки, спільні компоненти)
## Порція 3 — високий (whitelisted-методи, API, схема даних, публічні пакети)
- [ ] ... · зовнішні викликачі: так · потрібен перехідний період: так
```
Одна порція = одна знахідка або невелика група пов'язаних, щоб у разі поломки було легко знайти причину.

### 1.7 Зупинка
Покажи короткий підсумок: скільки модулів переглянуто, скільки знахідок кожного типу, кількість порцій, відкриті питання. Запитай:
- чи погоджується з цільовими інтерфейсами;
- які порції або пункти виключити;
- чи починати виконання.

**Не змінюй жодного файлу коду до явного «так».**

## Фаза 2. Виконання (після «так»)

1. Створи окрему гілку `refactor/general-purpose-<дата>`.
2. Перед першою порцією запусти тести, перевірку типів, лінтери, збірку і запиши вихідний стан. Те, що падало до тебе, — не твоя поломка, але згадай це у звіті.
3. Якщо код, який змінюєш, не покритий тестами, спершу додай мінімальні тести на поточну поведінку (характеризаційні), щоб рефакторинг мав страховку.
4. Для кожної порції:
   - Додай новий примітив поруч зі старим інтерфейсом.
   - Переведи викликачів на примітив; дію, яка раніше жила внизу, збери у викликача (або в тонкій функції верхнього шару).
   - Видали старі спеціалізовані функції, коли викликачів не лишилось. Для публічного API залиш стару точку як тонку обгортку над новою, познач застарілою (`@deprecated` / коментар) і запиши в звіт.
   - Знайди залишки: рядкові посилання (`frappe.call({method: '...'})`, `hooks.py`, динамічні імпорти), тести, моки, документацію.
   - Запусти тести, перевірку типів, лінтери, збірку.
   - Успіх → окремий коміт `refactor: <що> → <на що>`, відміть пункт у PLAN.md.
   - Поломка → відкоти порцію (`git restore` / `git reset` до попереднього коміту порції), опиши причину і спитай, що робити далі.
5. Рефакторинг не змінює поведінку. Якщо помітив баг — запиши окремо, не виправляй тут.
6. Наприкінці створи або онови `docs/MODULE-DESIGN.md` — короткий посібник: які примітиви має кожен перероблений модуль, де живе політика, і чотири питання для нового коду.

## Пастки
- **Надмірне узагальнення.** Мета — простіший інтерфейс, а не «фреймворк на майбутнє». Якщо пропозиція додає generic-параметри, реєстри, конфіги чи плагінні точки, яких сьогодні ніхто не потребує, — спрости.
- **Перенесена складність.** Якщо після рефакторингу кожен викликач пише ті самі 5 рядків, складність просто переїхала вгору. Тоді винеси спільну політику в одну функцію верхнього шару.
- **Динамічні виклики.** Шляхи функцій у рядках (`frappe.call`, `hooks.py`, `doc_events`, `scheduler_events`, `import()` з шаблонним рядком) пошук за іменем не знайде — шукай також частини шляху.
- **Зовнішні споживачі.** Whitelisted-методи і REST кличуть інші сервіси, мобільні застосунки, Client Script у базі даних (Frappe зберігає Client Script і Server Script у БД, вони не лежать у репозиторії) — перевір їх на стенді.
- **Типи як частина інтерфейсу.** У TS зміна експортованого типу ламає викликачів так само, як зміна сигнатури.
- **Великі диффи.** Якщо порція зачіпає понад ~30 файлів, розбий її.

## Фінальний звіт користувачу
- Що змінено (кількість порцій, модулів, функцій до і після), що пропущено і чому.
- Як перевірено (тести, типи, лінтери, збірка — результат до і після).
- Ризики, що лишилися (динамічні виклики, зовнішні споживачі, застарілі обгортки).
- Наприкінці 3–6 речень простою мовою: що зроблено, навіщо, що це означає практично.
